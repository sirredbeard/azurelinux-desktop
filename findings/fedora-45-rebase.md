Fedora 45 rebase: findings and plan

Branch rebase/fedora-45. Written 2026-11-08. All package tests ran on the Arduino board (ventunoq) in Podman, resolving the aarch64 builds of the Azure Linux 4.0, Fedora, and RPM Fusion repos. The repo targets x86_64. Resolution behavior, sonames, and version locks carry over. Arch-specific packages do not, and the notes below call out each place that matters.

The short version

The rebase works, but it forces one decision: which Python the image runs. Azure Linux ships Python 3.14. Fedora 45 ships Python 3.15, and Fedora 45's installer, tuned, and flatpak support packages need 3.15. Only one python3 package can own /usr/bin/python3.

If Python stays with Azure Linux, the installed system keeps almost all of its Azure Linux core. 547 of 1,066 packages come from Azure Linux, against 646 of 1,199 in the Fedora 43 baseline. Only 21 packages flip to Fedora against their will. The cost lands on the installer: anaconda-live cannot be in the live image, and the kiwi installer environment cannot resolve at all.

If Python moves to Fedora, the whole image tips. 136 of 1,235 packages come from Azure Linux. The installer works. The claw-back list shrinks back to 124 names. The cost is the core: firewalld, audit, util-linux, and the lvm2 stack all flip with it, because their Python parts are version-locked to their C libraries.

A hybrid is possible and matches how the product already works. The kiwi installer environment is a separate package set from the system it installs. The installer ISO can run a Fedora-Python environment and lay down an Azure-Python system. The live ISO cannot split that way, because anaconda-live runs inside the live environment itself.

Method

scripts/podman-test-azl4-fedora45.sh on this branch adapts the repo's podman-test-azl4-fedora.sh to ARM and to a Fedora version switch. It resolves a package set with dnf5 --installroot inside a Fedora container, the same way the canary image builds its rootfs, then reports how many packages came from each repo. Three sets were tested: the live kickstart %packages list, the kiwi installer package list, and the canary pkglist.

The Fedora 43 baseline validates the method. Resolved on ARM, the kickstart set gives 1,199 packages: 646 Azure Linux, 552 Fedora 43, 1 other (shim). The shipped x86_64 live image has 1,267 packages: 697 Azure Linux, 553 Fedora 43, 17 other. Key packages match the shipped list on origin and version: glibc from Fedora, glib2 and systemd and NetworkManager from Azure Linux, the AZL kernel.

One baseline package cannot exist on ARM. azurelinux-desktop-policy is an x86_64 package that hard-requires 27 version-pinned x86_64 kmod packages and the exact AZL kernel build. It drops out of every ARM run. That is a property of the package, not a test artifact, and it does not affect the Fedora 45 questions.

What Fedora 45 changes upstream

Fedora 45 shipped 2026-11-03. GNOME 51, glibc 2.44, systemd 262, Python 3.15, OpenSSL 4.0, ICU 78. End of life 2027-12-08. Fedora 43 goes end of life in December 2026; endoflife.date says the 9th, the Fedora 45 schedule says the 16th.

Two packaged files moved. Fedora's GPG keys now live in /usr/share/pki/rpm-gpg; /etc/pki/rpm-gpg is empty in a stock Fedora 45 install. Fedora's own repo files now live in /usr/share/dnf5/repos.d; /etc/yum.repos.d is empty. This repo stages its own files under /etc in both cases, and dnf reads both locations, so the images keep working. Tests and scripts that grep Fedora's packaged paths need updating. This branch already adds RPM-GPG-KEY-fedora-45-primary to assets/pki/rpm-gpg.

Removed upstream, with no replacement and nothing obsoleting them: gnome-themes-extra and libvdpau-va-gl. Both sit in the kickstart and kiwi package lists today and must come out. Renamed or merged: elfutils-default-yama-scope is now yama-ptrace-enable. mesa-va-drivers is absorbed into mesa-dri-drivers, which Provides the old name. The gpgme2 name is gone; gpgme carries libgpgme.so.45. Boost is packaged per library now, not as a monolith. GNOME Software 51 dropped PackageKit and talks to dnf5daemon-server instead, so PackageKit leaves the set on its own. OpenSSL 4.0 is the default and an openssl3-libs package (3.5.9) covers stragglers. RPM Fusion's 45 mirrorlist still pointed at the development tree on 2026-11-08; their release lags Fedora's.

The three configurations tested

All counts are the kickstart set on aarch64, dnf exit 0 unless noted.

Baseline, Fedora 43 as shipped: 1,199 packages. 646 Azure Linux, 552 Fedora 43, 1 other.

Naive rebase, version numbers swapped and the current 141-name claw-back kept: fails. gnome-themes-extra and libvdpau-va-gl no longer exist, and the Python ABI conflict blocks resolution.

Path A, minimal: Python stays Azure Linux. The claw-back adds python3, python3-libs, tuned, tuned-ppd, and python3-perf to the current list. anaconda-live and totem come out of the set. Result: 1,067 packages. 185 Azure Linux, 878 Fedora 45, 4 other. 376 baseline Azure Linux packages flip to Fedora. The low Azure count surprises until the weak dependencies are counted: ibus leaves because Fedora's ibus needs its Python bindings at 3.15, and PackageKit leaves with GNOME Software's switch to dnf5daemon. anaconda-webui and the cockpit and qt6-qtwebengine trees leave with anaconda-live.

Path A, maximum preservation: the claw-back lists every package the baseline takes from Azure Linux, 627 names after iteration. Result: 1,066 packages. 547 Azure Linux, 517 Fedora 45, 2 other. 525 of the baseline's 646 Azure Linux packages stay. 21 flip. Same 191 baseline names leave the set as in minimal A, all from the Python fork: the anaconda-live tree, totem's libpeas tree, ibus, PackageKit. The canary package set resolves clean under the same configuration. Its census is 539 packages (296 Azure Linux, 242 Fedora 45, 1 other) with weak dependencies off, matching the canary rootfs install in containers/canary/Dockerfile; an earlier count of 640 was taken with weak dependencies on in the harness and overstated the set by the 101 packages only weak dependencies pull in.

Path B: Python moves to Fedora. The claw-back drops to 123 names: the current list minus the Python-locked families, plus fedora-release star, because the installer chain pulls fedora-release subpackages that fight azurelinux-release over os-release and the issue files. Result: 1,235 packages. 136 Azure Linux, 1,095 Fedora 45, 4 other. 496 flip. Only 41 baseline names leave, and most of those are the renames listed above, not losses. The tree stays whole; its ownership changes.

Reproducing these runs: the three final claw-back lists are preserved next to this document: fedora-45-excludes-a.txt (627 names, path A maximum preservation), fedora-45-excludes-b.txt (123 names, path B for the kickstart set), and fedora-45-excludes-b-kiwi.txt (113 names, path B after the installer set's extra flips). The B counts printed during the original session read 124 and 114; each file also carried a shell fragment that the session's counting treated as a name and that matched nothing in the solve, so the preserved lists hold the real entries. The path A list that shipped is this list plus the build phase additions, and it lives in the four synced locations named in the update plan below. Every number above came from scripts/podman-test-azl4-fedora45.sh on arm64: PKGSRC selects the package set (kickstart, kiwi, or canary), AZL_FEDORA_EXCLUDES_FILE points at one of the preserved lists, and setting F45_KEEP_INSTALLER keeps anaconda-live and totem in the Fedora 45 set instead of dropping them. The harness now fails on an unreadable override file instead of falling back to its built-in list, propagates the dnf and container exit codes instead of reporting a partial install as a successful run, and resolves the canary set with weak dependencies off, matching containers/canary/Dockerfile.

What flips and why, under maximum preservation

Six rounds of solver output produced the final 627-name claw-back. Each round named the next family. The 21 forced flips, with the reason for each:

glib2: nautilus in GNOME 51 needs glib2 2.89 or newer. Azure ships 2.86.5. The pin falls on a version floor, not a soname.
libicu: GNOME 51 links ICU 78. Azure ships 77.
libxml2: Fedora 45 ships 2.15.4 and the soname moves to libxml2.so.16. Azure ships the .so.2 line.
glycin-libs and glycin-loaders: snapshot and nautilus need the current glycin gtk4 library.
libdisplay-info: soname moves to .so.3.
fmt: soname moves to libfmt.so.12.
nettle: soname moves to libnettle.so.9.
libvpx: soname moves to libvpx.so.12.
gpgme and gpgmepp: soname moves to libgpgme.so.45.
llvm-libs and llvm-filesystem: soname moves to libLLVM.so.23.1.
lua-libs: Fedora 45's libinput, wireplumber, and highlight link liblua-5.5. Azure ships Lua 5.4.
accountsservice and accountsservice-libs: gdm 51 needs the newer accountsservice.
fuse3 and fuse3-libs: see below. The F43 fork cannot survive.
libcbor and libfido2: freerdp needs libcbor.so.0.14. Azure's libfido2 needs libcbor.so.0.12, and openssh-clients needs libfido2. The two libcbor builds cannot coinstall. libfido2 moves to Fedora's build, which uses 0.14; libfido2.so.1 does not change, so openssh stays Azure Linux.
boost-thread: Boost 1.90 per-library packaging. libphonenumber needs libboost_thread.so.1.90.0, which blocks evolution-data-server, which blocks the shell chain.

Two more flips are set-dependent. Sets that name curl directly (the canary list, the kiwi list) take Fedora's curl 8.21, which needs libnghttp2 1.69 and libpsl 0.23.1, both newer than Azure's. libnghttp2 and libpsl flip in those sets. In the kickstart set Azure's curl wins and they stay.

Families that were unpinned during iteration but stayed Azure Linux anyway, because the Azure build still satisfies Fedora 45's consumers: gvfs, wireplumber, the grub2 tools family, ffmpeg, xdg-desktop-portal, gnome-online-accounts, gtksourceview5, gjs, libinput, libgweather, highlight. Unpinning is not flipping. The claw-back only needs to name packages where Fedora's build would otherwise win and break something.

The fuse3 fork

This deserves its own section because it breaks in both paths and it broke the current design's neatest trick. Azure's fuse3 is 3.16.2 and provides libfuse3.so.3. Fedora 45's fuse3 is 3.18.3 and provides libfuse3.so.4. Azure core packages link the old soname: e2fsprogs, grub2-tools. Fedora 45 desktop packages link the new one: flatpak, the portals. In Fedora 43 both repos carried 3.16.2 builds, so the exact-version lock between fuse3 and fuse3-libs could be satisfied from either side and both sonames were served. In Fedora 45 the versions diverge, the lock makes the two fuse3-libs builds mutually exclusive, and one side has to move. In the kickstart set the whole fuse3 family goes to Fedora and nothing Azure-side notices, because e2fsprogs is not in that set. In the kiwi set e2fsprogs is a hard requirement of anaconda-install-env-deps, so the kiwi configuration must also give up e2fsprogs, e2fsprogs-libs, libss, and libcom_err to Fedora. Same shape as the Python families: an exact-version sibling lock turns one package's move into a family's move.

glibc side by side

No. Both repos ship a package named glibc, one build can be installed per architecture, and neither repo carries a compat-glibc. There is no supported way to run two glibc versions in one rootfs, and the question turns out not to matter. glibc symbol versioning runs one direction: a binary built against 2.42 or older runs on 2.44. Azure's own glibc is 2.42, the same upstream version Fedora 43 shipped, and nothing on the Azure side needs symbols newer than that. The image already runs Fedora's glibc today, 2.42-17.fc43. The rebase changes the version to 2.44-2.fc45, not the owner. Fedora does show what a real side-by-side looks like where upstream wants one: python3.14 exists in Fedora 45 as a versioned secondary interpreter next to python3 3.15. No equivalent exists for glibc, and none is needed. The toolchain follows the same logic. Azure's gcc stays; it builds against the system glibc headers it already targets, and the kmod builds insulate themselves by building against the Azure kernel only.

The installer

The kiwi set decides the Python question for the installer ISO on its own. Under path A it fails on exactly two problems after the curl flips are applied. First, python3-libdnf5: anaconda needs dnf5's Python bindings, Azure's build needs the Azure libdnf5 that this product's own excludes forbid, and Fedora's build needs libpython 3.15. There is no third build. Second, the fuse3 and e2fsprogs conflict above. Under path B the same set resolves after two more family flips: e2fsprogs (above) and lvm2. Azure's lvm2-dbusd is a Python program pinned to python(abi) 3.14, Fedora's needs lvm2 2.03.43 exactly, and lvm2 is claw-back core today. The lvm2 and device-mapper families flip together. Final kiwi result under B: 681 packages, 91 Azure Linux, 588 Fedora 45, 2 other, with anaconda-core, anaconda-tui, and anaconda-install-env-deps all at 45.30 from Fedora, which matches the current design's rule that the installer environment takes anaconda from Fedora.

The live ISO under path A loses anaconda-live, and with it anaconda-webui and the cockpit-based install flow. A live rebase on path A needs a different install story for the live image, or accepts the kiwi installer ISO as the only installer. That is a product decision, not a resolution problem.

The canary container under Podman

The task asked for test builds of the canary container in Podman on the board. An unmodified build of containers/canary/Dockerfile with podman build fails at the first RUN step, before any Fedora 45 question comes up. The Dockerfile deletes the Fedora repo files in the build container and copies in assets/yum.repos.d/azurelinux-desktop.repo, which hardcodes x86_64 baseurls for azl-base, azl-microsoft, fedora43, and fedora43-updates. On an aarch64 host dnf resolves x86_64 packages whose arch-tagged requirements cannot be met, and the host tooling install (curl, tar, python3, flatpak) fails. The build is x86_64-only by construction. The BuildKit secret mount on the rootfs step was never reached, so Podman's handling of it is untested either way. The Dockerfile header already says docker only, no nested podman. The package-level canary tests in this document are the ARM substitute: the harness resolves the canary's own pkglist the same way the canary build resolves its rootfs, and that set passes under the maximum-preservation configuration.

Update plan: kickstart (live ISO)

kickstart/azurelinux-desktop-live.ks carries most of it. The repo stanzas change names and URLs from fedora43 to fedora45 in both the install-time repos and the ones written to the target. The RPM Fusion lines take 45. The %packages section drops gnome-themes-extra and libvdpau-va-gl. Under path A the set does not resolve anaconda-live or totem, and the install-from-live story needs its replacement decided before this file is final. Under path B the package list barely changes. The %post key import names RPM-GPG-KEY-fedora-45-primary, already staged in assets on this branch.

assets/yum.repos.d/azl-desktop-fedora.repo and azurelinux-desktop.repo carry the same version swap: repo ids, baseurls, and the gpgkey path. azl-desktop-rpmfusion.repo takes the 45 mirrorlists, with the caveat that RPM Fusion had not published final 45 mirrorlists as of 2026-11-08. The kiwi flow's download1 baseurl pattern sidesteps the mirrorlist and is the safer template.

Update plan: kiwi (installer ISO)

kiwi/config.sh holds the build. Its repofrompath entries and setopt names move from fedora43 to fedora45 for the release and updates repos. FEDORA_EXCLUDES in config.sh takes the final list for the chosen path. The staged key name in the install loop becomes the 45 key. kiwi/azl-install.ks.in defines the same repos three times: the offline download, the repos written into the installed system, and the createrepo stage. All three move together. Under path B the installer environment keeps its current anaconda rule, anaconda from Fedora unmodified, and adds the e2fsprogs and lvm2 family flips described above. Under the hybrid as originally drawn, the installer environment would follow path B while the target system's repos follow path A. One correction to that drawing: FEDORA_EXCLUDES in config.sh drives the offline download for the target system, so it carries the target's list under any variant; a path B installer environment would be expressed in the kiwi description's own repository policy for its bootstrap and system sets, not in config.sh. The branch does not implement the hybrid: the installer environment and the target both run path A, for the reasons in the CI phase section below.

The claw-back list lives in four places that scripts/check-fedora-excludes-consistency.sh keeps in sync: the kickstart repo lines, FEDORA_EXCLUDES in kiwi/config.sh, azl-desktop-fedora.repo, and azurelinux-desktop.repo. Whatever list the chosen path produces (627 names for A, 123 for the B kickstart set, 113 for the B kiwi set after its extra flips) goes into all four, and the consistency script's expectations update with it. The two B lists differing is new; today the sets share one list. If the hybrid or B is chosen, the consistency script needs to grow a per-set list or the kiwi set needs to carry its extra flips as a separate named delta. Flagging that here because it is the one place the plan adds mechanism instead of editing values.

Recommendation and open items

Maximum preservation (path A) is the right target for the installed system. It keeps 547 Azure Linux packages, the Azure Python, the Azure firewalld and audit and util-linux, and it costs 21 forced flips, each with a named soname or version floor behind it. Pair it with the path B installer environment in the kiwi ISO. Decide the live ISO's install story before starting the live work; that is the only open design question the tests surfaced. (Superseded in part by the migration plan at the end of this document: the installer environment stayed on path A rather than pairing with B. The live install story is still open.)

Watch items. tinysparql stayed Azure (3.10.1) while localsearch flipped to Fedora (3.12.0) under path A. Resolution accepts the pairing on soname grounds; the two are version-locked in spirit and the pairing wants a runtime test. The results above are resolution and transaction tests on aarch64, per the task. Runtime behavior of GNOME 51 on the Azure kernel and the x86_64 build itself are the next round. Fedora 43 support ends in December 2026 either way, so the decision has a date on it even though Azure Linux keeps patching its own snapshot.

Live build follow-up (2026-11-08, later)

The ARM64 test build of the rebased live ISO (path A configuration, no Edge) found one real bug the resolution tests could not see. Anaconda adds its own localization packages to the payload: langpacks-en, langpacks-core-en, langpacks-fonts-en. The kickstart package list never names them, so the harness never resolved them. langpacks pulls the hunspell-en family from both repos at once. Fedora 45 emptied its hunspell-en monolith (the dictionaries live only in the per-locale splits now) and ships the splits at a 2026 version. Azure's monolith still ships the en_AU and en_CA dictionaries itself, and Azure's en_US and en_GB splits win their names on cost. The transaction dies on four file conflicts: en_AU.aff, en_AU.dic, en_CA.aff, en_CA.dic, Azure monolith against Fedora splits. The fix keeps the family on one side: hunspell-en-AU, hunspell-en-CA, hunspell-en-GB, and hunspell-en-US join the claw-back list in all four synced locations, so Fedora's splits cannot enter and the Azure monolith serves AU and CA. Commit b6404bd.

The same build session hit an environmental blocker on this board, recorded here so it is not mistaken for a rebase defect: anaconda's D-Bus module processes die at startup with SIGILL (once SIGSEGV), a different module each run (Runtime, Payloads, Localization, Users, Security), roughly five seconds in. Two of the first three attempts started clean and reached the package transaction, which is how the hunspell conflict was captured. The module binaries run clean in a plain container (twenty consecutive starts of the Users module, no signal deaths), and the same kickstart transacts clean under dnf in the harness. The board runs a vendor kernel (6.8.0-1089-qcom). Builds retry in a loop; the failure is in the build host environment, not in the package set.

The test build then exposed a second Fedora 45 break, this one silent. The install and squashfs completed, but lorax produced no ISO at all and still reported success. Its aarch64 template builds the boot image only when boot/efi/EFI/*/gcdaa64.efi exists in the installed system. In Fedora 45 the grub2 cdboot package ships that file only under /usr/lib/efi/grub2/ (as 1:2.12-83.fc45); the /boot/efi path is a ghost entry that a dirinstall never materializes, so the check fails and the whole EFI block is skipped. The x86 template has the same gate on gcdx64.efi, so the CI build would have produced no ISO either. The live kickstart now copies the gcd image from /usr/lib/efi into /boot/efi in %post (commit ec705da). The test ISO used for the boot check was assembled by hand from the completed build tree with the same file placement, since the payload itself was already correct: 547 azl4 packages against 522 fc45 and no fc43, azurelinux-release present and fedora-release absent, glibc 2.44 from Fedora, python3 3.14.3 and kernel 6.18.31 from Azure, hunspell family entirely on Azure.

Boot check (2026-11-08): the hand-assembled test ISO boots under QEMU (aarch64 virt machine, AAVMF, TCG emulation; the board has no /dev/kvm). Serial log shows the full chain: UEFI boots the CD, the live initrd reaches switch-root, the system comes up through livesys and gdm, and the product's azl-flatpak-appstream first-boot service runs. Periodic screendumps stayed black until the session composited, then showed the GNOME shell top bar with its clock, stable across frames about twenty minutes in. The boot is slow under emulation and that is the emulation, not the image.

CI phase (2026-11-09)

The branch was squashed to a single commit and the builds moved to GitHub Actions. Four runs tell the story. The containers run rebuilt the tool images from the Fedora 45 Dockerfiles and pushed build-lorax:f45 and build-kiwi:f45 to GHCR; containers.yml still tagged its pushes f43 and that is fixed in the same commit. Both ISO workflows now accept a build-only manual dispatch (release_tag stays empty, nothing is published), and the live workflow also uploads the LiveOS squashfs as its own artifact.

The ARM64 test workflow (new, dispatch-only; it also lives on main because GitHub only dispatches workflows present on the default branch) built the live ISO natively on an ubuntu-24.04-arm runner in about 25 minutes, first attempt, no anaconda module failures. Its rootfs census matches the local board build exactly: 1,082 packages, 547 azl4, 522 fc45, no fc43. Lorax produced the ISO itself this time, efiboot.img included, which is the grub CD image fix working through the real template path instead of a hand assembly. The CI squashfs booted under systemd-nspawn on the board: Azure Linux 4.0, graphical.target default, gdm and NetworkManager active, the azl-flatpak-appstream service active, and the only failed units auditd and audit-rules, which cannot run in any container because the audit interface belongs to the host kernel.

The product x86_64 live build also succeeded first try, ISO and squashfs as artifacts, 581 azl4 and 540 fc45 packages, no fc43, Edge present. The census runs higher than ARM because the product kickstart keeps the x86_64-only packages the ARM variant drops. anaconda-live is absent, as path A already recorded; the install story is still the open decision.

The installer build failed, and the failure is the most useful data in this section. Kiwi's system installation phase resolves the system package set from the description's repositories before the install kickstart's repo excludes ever apply, and it picked Azure's grub2-pc 2.12-46.azl4, whose exact-version requirement on Azure's grub2-tools-minimal cannot be met once the rest of the grub2 family resolves to Fedora 2.12-83. The grub2 family fork has to be settled for the kiwi system phase the way the kickstart already settles it for installed systems, or the BIOS packages have to leave that set. The harness missed this because it modeled the bootstrap package list, not the system phase. Filed here as the next fix; it does not block the live images.

Migration plan (2026-11-09)

State of the stack, per piece. The live images are done on both architectures. x86_64 builds in CI at 581 azl4 and 540 fc45 with native Edge Canary, and ARM64 builds at 547 azl4 and 522 fc45 with the census matching the local board build package for package. Tool images are on the f45 tags. The installer is the last piece: its grub2 knot is fixed in this branch (below) and a verification build is running. One correction to the CI section above: Fedora 45 GA ships the grub2 family at 1:2.12-81.fc45, not 2.12-83; the higher number came from an updates lookup and never existed in the frozen GA tree the builds resolve against.

The installer fix, resolved. Kiwi resolves the system package set from the description's repositories before the install kickstart's excludes apply, and kiwi has no per-repo exclude of its own, so the ownership decision has to be expressed in the package list itself. The chain that deadlocked: Azure's grub2-tools-minimal links Azure's fuse3-libs for the libfuse3.so.3 FUSE_3.0 symbol; Fedora 45's fuse3 3.18 dropped that symbol version, and the installer environment needs Fedora's fuse3. So the whole grub2 family moves to Fedora together, pinned to 1:2.12-81.fc45 in the kiwi description: grub2-pc, grub2-common, grub2-tools, grub2-tools-minimal, grub2-efi-x64, grub2-efi-x64-modules, grub2-efi-x64-cdboot. The Azure-only grub2 metapackage exact-locks its members and Fedora has no metapackage to pin, so it is dropped and every member named. fuse3 flips to Fedora on dependency grounds alone, no pin needed. Shim stays Azure. A dnf solve of the exact system list against the same four repositories passes: 514 packages, the whole grub2 family from Fedora, no conflicts. This supersedes the earlier recommendation of a path B installer environment; the installed system stays path A and the installer environment differs from it only in this one family, the same shape as the plymouth exception the description already carries. If a future Fedora rebase moves the GA grub2 build, the pins move with it; they name the frozen tree the kiwi repos point at, not a moving target.

Installer verification, continued (2026-11-09, later). The first three verification attempts never reached kiwi: the third-party asset step failed on repeated HTTP 504s downloading the Copilot CLI tarball from the GitHub runner, while the same asset downloaded clean from two other networks; that is recorded as a runner-side fetch failure, not a branch defect. Attempt 4 cleared that step and the kiwi system install, which proves the grub2 family fix above, and failed in config.sh's offline repository download on one solver problem: totem. Its libpeas Python loader hard-requires libpython3.15, and the claw-back keeps Azure's python3 (3.14), so Fedora's loader chain has no satisfiable end. The Showtime substitution failed the same way on the next attempt: Showtime 50.0 is itself a Python application and requires python(abi) = 3.15 outright. The video player line is therefore dropped from the installer package set: under path A the installed system ships without a dedicated video player, the same position as the live image, and both GNOME video applications are casualties of the Python fork rather than of packaging. The next attempt got past the solve and failed on a stale name instead: gnome-themes-extra, deleted upstream before Fedora 45, was still in the installer package list (the live kickstart dropped it during the rebase; the kiwi list was missed), and the offline download refuses an unavailable name. It is removed. The following attempt flagged the second stale name, libvdpau-va-gl, also deleted upstream before Fedora 45 (the download reports one unavailable name at a time, which is why it did not appear in the earlier log); it is removed as well. The next attempt got through the download (1,295 RPMs) and failed the offline-repo validation on a soname fork: Azure's e2fsprogs requires libfuse3.so.3, Fedora's flatpak and xdg-desktop-portal require libfuse3.so.4, and the two fuse3-libs builds (3.16.2-7.azl4, 3.18.3-1.fc45) cannot be installed together. Fedora's own e2fsprogs is built against the .so.4 library, so the whole e2fsprogs family (e2fsprogs, e2fsprogs-libs, libcom_err, libss: the subpackages version-lock to each other, which the first attempt proved by failing on libss alone) comes out of the claw-back list in all four synced locations and the installer target takes it from Fedora, the same call the branch already made for the grub2 family. The live image never hit the conflict: its set contains e2fsprogs-libs (no fuse binary) but not e2fsprogs itself, verified in the ARM64 census below. With that change the offline download and its validation pass end to end; the build then failed in kiwi's bootloader phase with "Signed grub2 efi loader not found", because Fedora 45's grub2 ships the signed loaders only under /usr/lib/efi and the /boot/efi copies are ghost entries no dirinstall materializes (the same gap the live kickstart already stages around for lorax). kiwi/config.sh now stages every signed loader from /usr/lib/efi into /boot/efi/EFI/<vendor> before kiwi's bootloader setup runs. A fresh verification build is running on that change.

The update path got its own test on the verified ARM64 image: boot the image under systemd-nspawn and run its own dnf against the live repos. `dnf upgrade --assumeno` completes safely (dnf skips what it cannot install and the rest updates normally), and every skip is a claw-back family freezing as a unit, in three shapes. Python-ABI freezes: python-unversioned-command, python3-pyinotify and python3-linux-procfs cannot take their Fedora builds because those need python(abi) = 3.15 and path A keeps python3 at Azure's 3.14. Version-locked partial families: the hunspell-en and Noto fonts updates need exact-version partners (hunspell-en-US, google-noto-fonts-common, default-fonts-core-sans) that the claw-back holds at Azure's builds. Paired conflicts: Fedora's crypto-policies update conflicts with openssh below 10.4p1, and both packages sit on the Azure side, so the pair freezes together. One case was a list bug rather than a trade: samba-common was not clawed back while samba-common-libs was, so dnf offered a Fedora samba-common it could never pair with the installed libs; samba-common is in the excludepkgs list in all four synced locations now. The frozen families are the standing cost of path A, paid as skipped updates for those packages only. A local reproduction of the offline download was attempted in Fedora containers and is not cited here: Fedora's dnf5/libsolv selects differently around the azurelinux-repos capability chain than the kiwi image's dnf5 does, so the local runs failed earlier than CI ever did, on a problem CI does not have.

ARM64 as a product, not a test. The ARM live workflow is dispatch-only and also lives on main; productizing it means a release path alongside the x86_64 one: same release, per-arch assets, the ARM ISO and squashfs named for aarch64 so Get-AzureLinuxDesktop and the release page can tell them apart. The ARM installer variant comes after: the kiwi description is x86_64-only today (grub2-efi-x64, shim-x64, x86_64 repo URLs) and needs its aarch64 twin with grub2-efi-aa64 and shim-aa64, with the same Fedora grub2 pinning at the aarch64 GA build. Hardware support is a separate claim from building the image, and findings/ventunoq-arm-hardware-enablement.md (PR #42) is its plan: backport the mainline monaco-arduino-monza device tree, and pass the 18-point no-loss checklist on the board before anyone calls the Ventuno Q supported. Phase 0 of that plan is done, with results in the PR #42 findings: the shipped kernel already carries WLAN, Bluetooth, and UVC, so sound is the only out-of-tree kmod family left to build; the DSP firmware and the ALSA topologies come from Fedora 45's qcom-firmware, which co-installs clean with Azure's linux-firmware; the remaining packaging is the FastRPC userspace, qrtr-ns, and a UCM profile for the board's audio card. The image builds today; the board support lands when the checklist passes.

Edge on ARM64. There is no Edge build for arm64 Linux, official or otherwise. The ARM image now takes edge-arm-bridge from its GitHub Pages RPM repo, added to the ARM kickstart variant in make-arm-ks.py alongside the package: FEX runs the x86_64 Edge build, and the bridge service mirrors the profile into native Chromium. The RPMs were verified installing clean inside this rebase's ARM rootfs, and plain dnf installs from the published repo were verified the same way. The x86_64 image keeps native Edge Canary and does not change. One untested piece, recorded plainly: the headed first sign-in from the installed RPM on a real desktop has only run in containers.

Copilot on ARM64. copilot-desktop-gtk merged its dual-arch pipeline (PR #12 there): a multi-arch builder image and a per-arch signed repo layout with repo-aarch64 alongside repo. v0.1.21 published on 2026-11-09 as a pre-release, and the ARM image prestages the aarch64 build from repo-aarch64 the same way x86_64 prestages from its own repo: the install helper takes a repo suffix, the prestage runs inside the ARM build with its AppStream paths on aarch64, and the built image's system Flatpak shows Copilot 0.1.21 on aarch64 (verified under systemd-nspawn). Its Wine AppImage experiment was built and verified on both architectures and then cancelled, the AppImage release was deleted, and no WinFile artifact ships in this image on either architecture. Field issues from the first test round (2026-11-09, later)

Hayden booted the x86_64 candidate on his test box: sound, keyboard backlight, camera, Bluetooth, and the plain Copilot app all work, and it boots to GNOME. Four defects came back from that round, plus the ARM package set found two more of its own. This section is their record. The ARM items live in the PR #42 findings; the four below are this branch.

dnf upgrade stopped on 22 problems. The claw-back had frozen half of several version-locked families: samba-common without the rest of samba, python3 without the packages bound to it's ABI, google-noto-fonts-common without the vf fonts that require it exactly. A family split across the claw-back line can install, because each half satisfies the other at the frozen version, and then can never update. Commit 7b1ce1b adds 27 names to the exclude list in all four synced locations (668 total): the rest of samba, the python 3.15 dependents, at-spi2-core/at-spi2-atk/atk, perl-Data-Dumper, hypervfcopyd, hunspell-en, the noto vf fonts, the langpacks-en set, and crypto-policies with it's scripts package, whose Fedora build conflicts with the Azure openssh. The proof is a container solve against a copy of the burned candidate rootfs: with the old list it reproduces Hayden's 22 problems line for line, with the new list it solves clean.

The GitHub Copilot GUI was missing from the live image, and the cause was two layers deep. The GUI package (named github, version 1.1.35) ships /usr/bin/github, and so does github-desktop, which the main transaction installs first. The kickstart %post's rpm -i hit the file conflict and installed nothing: a %post failure does not fail the lorax build, and the follow-on configure script masked the miss because it's /usr/bin/github check passed against Desktop's symlink. Commit f7d06d5 installs with --replacefiles in both kickstarts and asserts the package and the desktop file landed. The verification build still shipped without the app, and the image's own /var/log/azl-desktop-post.log says why: 'package github-0:1.1.35-1.x86_64 does not verify: no signature'. GitHub ships that RPM unsigned and the image verifies signatures. Commit 208d332 adds --nosignature next to --replacefiles and makes the checks exit explicitly, because a bare test in %post only logs. Verified in live build 42719757690: the desktop file is present, github 1.1.35-1 is in the rpmdb, /usr/bin/github belongs to the github package, and github-desktop is intact. The installer carries the same fix by construction: it's rendered install kickstart runs the same commands against the staged RPM, and the installer ISO's staged payload is the same 1.1.35 package (installer build 42729996317, introspected after the fact).

The gh-cli repo key had expired. GitHub's published keyring rotated: the old key (created 2022-09-06) expired 2026-09-05, and the successor (rsa4096, created 2026-04-07, fingerprint 7F38 BBB5 9D06 4DBC B3D8 4D72 5612 B364 6231 3325) signs it now. Commit 79899ea ships the current keyring file in assets/pki/rpm-gpg. Both keys sit in the one file, which is normal for a rotation. Verified in the live build above and in the installer ISO's staged assets.

VS Code on the live ISO asked to unlock the 'Login' keyring, and cancelling the prompt destabilized the editor. The shipped helper, /usr/libexec/azl-keyring-empty-unlock, fired once at session start: it waited up to ten seconds for the secrets socket, sent the empty-password unlock, and exited. When gnome-keyring-daemon's own component autostarts replaced the instance afterwards, the replacement came back locked and nothing retried. PAM cannot seed the keyring on the live image because the live session autologins and liveuser is created at boot, so there is no password to seed with at build time. Commit 0ad32b2 rewrites the helper: it waits up to 30 seconds for the socket, then loops for about 150 seconds, sending the unlock and reading the login collection's Locked property over the session bus after each attempt, and exits only when the collection reads unlocked. The autostart entry moves to the Initialization phase so the helper starts before the components it races. The assets feed both kickstart paths. Presence is verified in both images; the behavioral test is a boot of the live image, which rides the next manual QA round.
